# 6. Match transit stops to stations by location, using a station registry

- **Status:** Accepted
- **Date:** 2026-10-27

## Context

The prototype matched Google's stop names to Metro station names with string normalisation.
When a name doesn't match, the station is silently treated as fine. Train direction was also
compared as free text (Google headsign vs. "dirección X" in elevator descriptions).

## Decision

- Build a **station registry** (`packages/registry` → `stations.json`) with stable station IDs,
  coordinates, lines, platforms keyed by terminal station ID, device IDs, and name aliases.
  It is generated by a script, validated by a schema, and committed so changes are reviewable.
- Match a routing stop to a station **by location first** (nearest within ~150 m), using the name
  only to break ties.
- Resolve headsigns and "dirección X" texts to **terminal station IDs** via the alias table;
  compare IDs, not strings. Each leg is evaluated with its own direction.
- A stop that can't be matched yields `unknown` ([ADR 0005](0005-tri-state-accessibility-verdict.md)) and is logged.

## Consequences

- Matching becomes deterministic and testable; misses are visible and fixable.
- The registry must be regenerated when the network changes (e.g. a new line opens).
- Requires requesting stop locations from the routing provider.
